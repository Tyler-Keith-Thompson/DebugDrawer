# Changelog

Notable changes in each release, newest first, in the style of
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/). Work lands under Unreleased; before
`just deploy`, rename that heading to the new version and date (`## [0.1.2] - 2026-11-17`), start a
new empty Unreleased above it, and commit. Deploy refuses to tag a version with no entry here, and
the entry becomes the GitHub release's notes.

## [Unreleased]

### Added

- DD-107: the device-lab bridge. A sidecar shares the session it opens with a Mac viewer over the local network, so one Mac sees and drives production builds on many devices, while the production app's receiver still talks over the app group alone and opens no listener. `.debugDrawerSidecarRelay(_:startsServing:)` on `DebugDrawerSidecarView` gives each app's screen a Mac Viewer control (Start Serving, each Mac's pairing code with Reject, each paired Mac with Disconnect); without it nothing listens. `DebugDrawerSidecarRelay(connection:configuration:)` is the relay itself (`start()`, `stop()`, `server`, `snapshot`): a `DebugDrawerNetworkServer` that serves, under each capability's own ID, what the app serves that the open session may read (under a grant policy, what the grant lists), once the app's first snapshot of it arrives, and carries a viewer's commands back as the sidecar's own, for the receiver to apply or refuse and audit; as the session ends, reaches its expiry date or serving stops, everything is dropped and the next session starts from a new transport. Its own `DebugDrawerSidecarRelay.Snapshot` (the app, `sessionExpires`, `pluginIDs`) is served under `DebugDrawerSidecarRelay.pluginID`; the sessions aren't relayed. `DebugDrawerSidecarPlugin.plugin(over:)` makes any kit plugin over a transport of the caller's, such as a paired `DebugDrawerNetworkTransport`. The kit now depends on `DebugDrawerRemote` on macOS and iOS (not watchOS, which doesn't build it). `scripts/modules.py` checks that nothing a release build links reaches `DebugDrawerRemote`, and `//Example:receiver_listener_test` that the production host's binary loads no Network.framework and holds no listener symbol. `Example/Sidecar` carries the modifier (`-ShareWithMac`, `-RemoteViewersOnLoopback`, `-MacViewerPort`) and declares `NSLocalNetworkUsageDescription` and `NSBonjourServices`; the macOS example's Remote window shows a relayed app's shared capabilities with the kit's plugins until the session ends. SecurityModel.md covers the Mac viewer as a party to the session.
- DD-105: the example sidecar takes `-ScriptSession <bundle ID>`: it opens a session with that app, overrides the `new-checkout` flag, ends the session and waits for the host to put the flag back, logging each step and the channel that carried it, so a run on the Mac shows the pair communicating with no one at the screen.
- DD-265: `DebugDrawerSidecarKit` ships a plugin for every capability the receiver ships, so a company's sidecar no longer writes its own: `DebugDrawerSidecarPlugin.featureFlagOverrides` (Flags: a switch, or a field and Set for a number or a string, Clear, Clear All Overrides), `.experimentOverrides` (Experiments: a variant picker each, Clear, Clear All Overrides), `.logLevels` (a level picker per subsystem, Reset, Reset All Levels), `.tweaks` (each production-safe tweak's own control, Reset, Reset All), `.localizationReview` (Strings: the review mode), `.accessibilityEnvironmentOverrides` (Dynamic Type, Increase Contrast and Reduce Motion, Reset), `.analyticsEvents` (the session's events with their properties, Clear), `.metricKitPayloads` (payloads with Copy JSON and Delete, Delete All; Create Report adds each as JSON), `.networkMocking` (the allowed hosts, the session's rules and delays with a switch and Remove, a form for a new rule and for a delay, Reset) and `.networkMocking(presets:conditionPresets:)` (the team's own rules and delays as one-tap additions), `.diagnosticsCapture` (Start Capture, the lines and requests, Stop and Delete; Create Report adds `console.txt` and `network.json`) and `.pushRegistration` (the device token with Copy Token, the APNs server, the notification settings, Refresh). The kit now depends on the UI-free capability modules (`DebugDrawerTweaks`, `DebugDrawerAnalytics`, `DebugDrawerLocalization`, `DebugDrawerAccessibility`, and, on macOS and iOS only, `DebugDrawerMetricKit`, `DebugDrawerNetwork` and `DebugDrawerNotifications`, which watchOS doesn't build, so a watch sidecar has no MetricKit, Mocking or Push Registration plugin). Release builds keep each member over a plugin that draws nothing. `Example/Sidecar` lists the kit's plugins and keeps only its app file, its grant server and Mocking's presets.
- DD-261: a watch sidecar is built on `DebugDrawerSidecarKit`, which now builds for watchOS (`just build`, `just build-spm`). There it hosts the plugins that build on watchOS: the receiver's `.bugReports`, `.scenarios`, `.authActions`, `.appStateReset`, `.environments`, `.userDefaults`, `.locationSpoofing` and `.appState`, and any `DebugDrawerSidecarPlugin` of the host's own; `.console`, `.network` and `.performanceTraces` don't exist there, as Console, Network and the Hang Detector don't build for watchOS, so `DebugDrawerSidecarView`'s `plugins` defaults to none on watchOS (Console and Network elsewhere, as before). `DebugDrawerSidecarView` takes the watch's navigation model there: a list of the apps, each row opening the app's screen, which lists its version and channel, its session with Open Session or End Session below it, a row per plugin that opens the plugin, and Create Report. `DebugDrawerSidecarApp.open(url:)` returns `false` on watchOS, which opens no other app. `DebugDrawerAppInfo`, `DebugDrawerLocation` and `DebugDrawerAppStateReset` also build for watchOS. The kit takes Reset App State's types from `DebugDrawerAppStateReset` rather than from its plugin. The kit's tests run in the watchOS simulator too. In Package.swift the Console, Network and Hang Detector plugins link OSLogClient, `DebugDrawerNetwork` and `DebugDrawerHangDetector` on the plugins' own platforms (macOS, Mac Catalyst and iOS), as Xcode would otherwise build those for the kit on watchOS, where the plugins themselves are left out.
- DD-247: `RemoteViewingPlugin(server:)` (`DebugDrawerRemote`) shows a `DebugDrawerNetworkServer` in the drawer, so a host no longer writes its own pairing plugin: whether the server listens, on which port and address and whether Bonjour advertises it, with Start Serving (and why a start failed) and Stop Serving; each viewer asking to pair with its name, its six-digit code (read out digit by digit) and Reject; each paired viewer with Disconnect. Its badge counts the viewers waiting for their code, in the drawers that installed it over that server only. Release builds get a stand-in that draws nothing. The example apps use it in place of their own.
- DD-246: a Mac can show a paired device's Network and Console live. `NetworkPluginView(transport:)` and `ConsolePluginView(transport:)` are public views over any `DebugDrawerTransport` (a `DebugDrawerNetworkTransport` once paired, or a sidecar's): they show "Waiting for Network…" (or Console) until the app's model answers, then draw what the app's drawer draws, sending each command back, and say why when the model isn't reached; they intercept and capture nothing in the viewer's process, and draw nothing in release builds. The macOS example app gains a Remote window (Debug > Remote Viewer, or `-OpenRemoteViewer`) that lists the devices `DebugDrawerNetworkBrowser` finds once asked to look, connects to one or to an address, asks for the code and shows the device's Network and Console side by side; the macOS and iOS examples serve themselves through a Remote Viewing plugin in their drawer that starts the server and shows each viewer's code (`-ServeRemoteViewers`, `-RemoteViewersOnLoopback`), and declare `NSLocalNetworkUsageDescription` and `NSBonjourServices`.
- DD-122: location spoofing for release builds, to test geo features on the build that ships, off unless the host enables it and high risk. `DebugDrawerLocation`, a new library a release build links beside the receiver (macOS and iOS, like its plugin), holds `LocationCoordinate` (moved from the Location plugin, now public, with `init(_:)` from a `CLLocationCoordinate2D` and `isValid`; the plugin re-exports the module, so `import DebugDrawerLocationPlugin` sees it too) and `LocationSpoofing`: the host passes the readings a tester may move through `location(replacing:)` / `locations(replacing:)` (nonisolated, from any thread; nothing is intercepted, and the plugin's swizzles stay debug-only) and is told through the required `spoofingDidChange` closure, on the main actor, with the spoofed location as a spoof lands or moves and `nil` as it ends, so its own fraud checks can react; `isSpoofing`, `spoofedLocation` and `snapshot.isSpoofing` say the same. `receiver.enable(.locationSpoofing(spoofing))`, served under `"DebugDrawer.LocationSpoofing"` (`Snapshot { coordinate; isSpoofing }`, `Command.spoof(_:)` / `.stop`): a coordinate off the Earth is refused `malformedCommand`, not enabled `unknownCapability`, and a spoof the model is handed outside a session is ignored. Under a grant policy a spoof needs a grant listing the capability; `.requiringGrant()` needs one even without a policy. Always session-scoped: the readings are real again, and the host told, as the session ends, expires or a gate turns off, and readings stop being spoofed at the session's expiry date even before its timer fires; the coordinate lives in memory only, and a flag kept in the defaults while spoofing (`DebugDrawer.LocationSpoofing.isSpoofing`) has the next launch tell the host `nil` as it makes the capability after a kill. The kit gains `DebugDrawerSidecarPlugin.locationSpoofing` (a high-risk warning, latitude and longitude fields, five places, Stop Spoofing); Example/Receiver's store finder follows a spoof, raises a fraud signal and names the location in its session indicator, and Example/Sidecar lists `.locationSpoofing`.
- DD-127: allowlisted UserDefaults viewing and editing for release builds, off unless the host enables it (risk medium: whoever holds the sidecar can change any allowlisted value, and what the app derives from it, but can't read or write any other key). The host declares each key with its kind (`DebugDrawerUserDefaultsKey`, in `DebugDrawerReceiver`: `.string(_:title:maximumLength:)`, `.integer(_:title:in:)`, `.double(_:title:in:)`, `.bool(_:title:)`, `.choice(_:title:options:)`) and calls `receiver.enable(.userDefaults(.choice("plan", options: ["free", "pro"]), .bool("showsTips")))` or `.userDefaults(DebugDrawerUserDefaults(...))`; enabled with no key it lists nothing. Served under `"DebugDrawer.UserDefaults"` (`Snapshot { entries, editedKeys }`, `Command.set(key:value:)` with a `DebugDrawerUserDefaultsValue` (`.string`, `.integer`, `.double`, `.bool`, encoded `{"integer":3}`), `.remove(key:)`, `.revertAll`): the domain is never listed, a key reads as its declared kind only, an unlisted key is refused `notExposed`, a value of another kind or out of bounds `malformedCommand`, not enabled `unknownCapability`. A repeated, empty or DebugDrawer-prefixed key, a choice without options and a bound that isn't finite trap. `DebugDrawerAuditEntry` gains `changes: [Change]?` (key, `oldValue`, `newValue`), filled for each edit (`commandApplied`) and the session's revert (`changeReverted`), left out of the JSON when `nil`, so logs written before decode, plus `init(date:sessionID:capability:event:changes:)` beside the existing initializer. Edits last for the session by default, from a record of each key's original kept in the same defaults (`DebugDrawer.UserDefaults.originalValues`): put back as the session ends, expires or a gate turns off, and as the next launch makes the capability after a kill; `scope: .persistent` keeps them until a sidecar sends `revertAll`. Never allowlist a secret: values are shown to the sidecar and written to the audit log. The kit gains `DebugDrawerSidecarPlugin.userDefaults` (an editor per kind, Remove, Revert All); Example/Receiver allowlists its plan, tips and items-per-page settings, shown on its screen, and Example/Sidecar lists `.userDefaults`.
- DD-126: a read-only snapshot of the app's state for release builds, shown in the sidecar during its session and attached to every report the sidecar creates, off unless the host enables it (risk low). `AppInfoBuildMetadata` moves into `DebugDrawerAppInfo`, a new library a release build links beside the receiver (macOS and iOS, like its plugin), its Info.plist reading now real in every build; `DebugDrawerAppInfoPlugin` re-exports it, so plugin users change nothing. The host makes a `DebugDrawerAppState` with the receiver's sessions and calls `receiver.enable(.appState(appState))`; it is served under `"DebugDrawer.AppState"` (`Snapshot { sessionID, state }`, one command, `.refresh`, scope persistent) only while a session is open, and under a grant policy only to a session whose grant lists it. The `State` holds the bundle ID, version, build, build metadata (commit, branch, CI build) and when it was read, and only what the host registers beside them: `featureFlags:` (the flags a `DebugDrawerFeatureFlagOverrides` overrides now), `experiments:` (every experiment of a `DebugDrawerExperimentOverrides` with its bucket and whether it is forced), `environments:` (the active one of a `DebugDrawerEnvironments`), `userID:` (hashed in the process with HMAC-SHA256 under 32 random bytes the install keeps in the app's own defaults, so one install's reports correlate and no raw ID leaves the app) and `values:` (`DebugDrawerAppStateField`s, a key and a closure returning a `DebugDrawerAppStateValue`: a string, a number or a Boolean; never a secret). The registered models are read, never copied, and followed during the session. `read()` gives the state at any time, for the host's bug reports (`DebugDrawerBugReports(sessions:) { appState.read() }`). The kit's `DebugDrawerSidecarPlugin.appState` shows it with Refresh, and `DebugDrawerSidecarView` hosts it as the app is reached, so Create Report adds `App State/app-state.json` (redacted) to every report. Example/Receiver registers its flag and experiment overrides, backend, a fake user ID and two values, and puts the state in its bug reports; Example/Sidecar lists `.appState`.
- DD-125: performance traces and hang reports for release builds, during a sidecar's session, off unless the host enables it. The Hangs plugin's monitor (the main run loop observer and the watcher thread that samples the main thread's stack) moves into `DebugDrawerHangDetector`, a new library a release build links beside the receiver, real in every build (the plugin re-exports it, so `import DebugDrawerHangDetectorPlugin` compiles unchanged). The host makes a `PerformanceTraces` with the receiver's sessions (`hitchThreshold:` 100 ms and `hangThreshold:` 250 ms by default, `limits:` `.standard` = 50 stalls, 500 intervals) and calls `receiver.enable(.performanceTraces(traces))`, and marks intervals with `beginInterval(_:)` / `endInterval(_:)` (shaped as `OSSignposter`'s, named by a `StaticString`, callable from any thread). Served under `PerformanceTraces.pluginID` (`"DebugDrawer.PerformanceTraces"`; `Snapshot { sessionID, executable, hitchThreshold, hangThreshold, stalls, intervals, droppedStalls, droppedIntervals, limits, exports; isRecording, text }`, `Command.start`, `stop`, `export`): nothing runs (no observer, no thread, no interval kept) until a sidecar sends `start` in an open session, and the monitor stops and the recording is deleted as the sidecar stops it, as the session ends or expires, as a gate turns it off, and, after a kill, as the next launch enables the capability. Each `Stall` is a `.hitch` or `.hang` with when it began, its duration and the main thread's `Frame`s, each with its address, image, image UUID, offset into the image and nearest exported symbol, so a stripped build's frames symbolicate with its dSYM; `Snapshot.text` (the report's `performance.txt`) ends with the binary images' load addresses and UUIDs for `atos`. Risk: low, a sidecar sees stacks and timings of the app's own code. The overhead while recording is measured by `PerformanceTracesOverheadTests` in an optimized build and documented in the README and on `PerformanceTraces`. `DebugDrawerSidecarKit` gains `DebugDrawerSidecarPlugin.performanceTraces` (Start Recording, each stall open to its stack, the intervals, Stop and Delete, and `performance.txt` in Create Report); Example/Receiver gains Freeze for 2 s and a signposted Load Report, and Example/Sidecar lists the plugin.
- DD-120: environment switching for release builds, to dogfood a production build against a staging or canary backend, off unless the host enables it and high risk. The host lists its environments (`DebugDrawerEnvironment`, in `DebugDrawerReceiver`: an ID, a title and a summary, no URL) and maps each ID to its own configuration in a `DebugDrawerEnvironmentAdapter` (`activate(_:)`), then calls `receiver.enable(.environments(default:allowing:_:adapter:))` or `.environments(DebugDrawerEnvironments(...))`. The allowlist is mandatory: the default and at least one allowed environment are separate parameters, so an empty list doesn't compile, and a repeated ID (the default's included) or an empty one traps. Served under `"DebugDrawer.Environments"` (`Snapshot { environments, defaultEnvironment, activeEnvironment; isSwitched }`, `Command.activate(environment:)` / `.reset`): a command carries an ID only, an unlisted one (an address among them) is refused `notExposed`, not enabled `unknownCapability`, and the adapter is handed the host's own value. Under a grant policy a switch needs a grant listing the capability; `.requiringGrant()` needs one even without a policy. Always session-scoped: the default comes back as the session ends, expires or a gate turns off, and, from a record kept in the defaults (`DebugDrawer.Environments.activeEnvironment`, written before the switch), as the next launch makes the capability after a kill. Show `snapshot.isSwitched` in the host's session indicator. The kit gains `DebugDrawerSidecarPlugin.environments` (a high-risk warning, the active environment marked, Switch and Reset to Default); Example/Receiver switches between Production, Staging and Canary (fake base URLs shown in the host only) and names the backend in its session indicator, and Example/Sidecar lists `.environments`.
- DD-118: app state reset for release builds, from a sidecar, off unless the host enables it; DD-119's cache clearing is part of it (an app that allows only `.caches` and `.urlCache`). The Reset App State plugin's UI-free part moves into `DebugDrawerAppStateReset`, a new library a release build links beside the receiver (`AppStateReset`, `AppStateReset.Category` and `AppStateReset.Cleanup`; the plugin re-exports it, so `import DebugDrawerAppStateResetPlugin` compiles unchanged, and `ResetCategory` is now `AppStateReset.Category`). The host makes an `AppStateResetRequests` with the receiver's sessions and the categories it allows (`allowing:`; `Set<AppStateReset.Category>.all` is every category but the keychain, which is allowed only with `allowingKeychain: true`, and naming it in `allowing:` traps; App cleanup only with a `cleanup`), and calls `receiver.enable(.appStateReset(requests))`. Served under `AppStateResetRequests.pluginID` (`"DebugDrawer.AppStateReset"`; `Snapshot { sessionID, allowed, activity, listing, lastReset, launchURL }`, `Command.refresh`, `reset(_:)` of `Confirmation`s, `cancel`), nothing is read until a sidecar refreshes in a session; the listing names each category's keys, top-level files with their sizes, cookie domains and keychain services or labels (never an account, never a value; at most 500 a category, with a count of the rest) and a revision per category over those names. A reset is refused as `unknownCapability` before the capability is enabled, `notExposed` for a category the host didn't allow, `malformedCommand` when empty or naming a category twice, and as the new `DebugDrawerAuditEntry.Refusal.staleConfirmation` at another revision than the listing's; it waits for the app's next foreground (or runs at once there), is dropped when the session ends first, reads every category again and deletes nothing when a confirmed one changed (`Outcome.notApplied(changed:)`), and otherwise reports what each category cleared and couldn't (`Outcome.applied(_:)`). DebugDrawer's own keys (`com.debugdrawer.`, `DebugDrawer.`) and files and the receiver's store stay, so the session and the audit log survive. Risk: data loss on the employee's own device. `DebugDrawerSidecarKit` gains `DebugDrawerSidecarPlugin.appStateReset` (a checkbox per allowed category, a confirmation listing every item, Reset, which brings the app forward, Cancel while it waits, and the last reset). The example host allows UserDefaults and caches and seeds some of each; the example sidecar lists the plugin.
- DD-117: auth actions for release builds, to test how the app handles an expired access token, a forced refresh or a log out, off unless the host enables it. The host registers actions on its own sign-in (`DebugDrawerAuthAction`, in `DebugDrawerReceiver`: the well-known `.expireAccessToken`, `.forceRefresh` and `.logOut`, with IDs `expire-access-token`, `force-refresh` and `log-out`, or `init(_:title:summary:handler:)` for one of its own), each a main-actor `async` handler that takes nothing and returns `DebugDrawerAuthAction.Outcome` (`.succeeded`, or `.failed(_:)` with a `StaticString` message, so no value the app holds at run time can reach the sidecar through it), and calls `receiver.enable(.authActions(_:launchURL:))` (or `.authActions(model)` over a `DebugDrawerAuthActions`). Served under `DebugDrawerAuthActions.pluginID` (`"DebugDrawer.AuthActions"`; `Snapshot { actions, launchURL }`, each `Entry` with its `lastRun`, a `Run` whose `status` is `running`, `succeeded` or `failed(message:)`, cut to 200 characters; `Command.perform(action:)`), a request in a session runs the handler; the receiver never sees a token and the snapshot has no field for one. An action the host didn't register is refused as `notExposed`, a request before the capability is enabled as `unknownCapability`; requests are audited as `commandApplied` and aren't reverted (scope `.persistent`); `.requiringGrant()` makes them need a grant. Risk: low, an employee can log themselves out. `DebugDrawerSidecarKit` gains `DebugDrawerSidecarPlugin.authActions` (a button per action, which sends the request and brings the app forward, and each action's last result). The example host shows a fake sign-in as signed in, expired or signed out, never its token; the example sidecar lists the Auth plugin.
- DD-116: a scenario launcher for release builds, off unless the host enables it. The host registers named scenarios (`DebugDrawerScenario`, in `DebugDrawerReceiver`: an ID, a title, a summary, declared parameters and a main-actor handler of its own) and calls `receiver.enable(.scenarios(_:launchURL:))` (or `.scenarios(model)` over a `DebugDrawerScenarios`). Parameters are named and typed (`DebugDrawerScenarioParameter.string(_:title:default:maximumLength:)`, `integer(_:title:default:in:)`, `boolean(_:title:default:)`, `choice(_:title:options:default:)`; a declaration that contradicts itself traps) and values are `DebugDrawerScenarioValue` (`string`, `integer`, `boolean`). Served under `DebugDrawerScenarios.pluginID` (`"DebugDrawer.Scenarios"`; `Snapshot { scenarios, launchURL, lastRun }`, `Command.run(scenario:arguments:)`), a launch in a session runs the handler with `DebugDrawerScenario.Arguments` holding a checked value for every declared parameter (the default for one left out), read typed through `string(_:)`, `integer(_:)`, `boolean(_:)`; nothing received is evaluated. - DD-115: employees can aim a test push at their own device from a sidecar, on a release build, off unless the host enables it. `DebugDrawerNotifications`, a new library a release build links beside the receiver (macOS and iOS, like its plugin), holds `NotificationSettings` (moved from the Notifications plugin, now public and `Codable`; the plugin re-exports the module, so `import DebugDrawerNotificationsPlugin` compiles unchanged) and `PushRegistrationMirror`: the host makes it with the receiver's sessions, calls `receiver.enable(.pushRegistration(mirror))`, and hands it the token from `application(_:didRegisterForRemoteNotificationsWithDeviceToken:)` (`didRegisterForRemoteNotifications(withDeviceToken:)`, `didFailToRegisterForRemoteNotifications(withError:)`). The charter's "never expose secrets (tokens) over IPC" is read as credentials: a device token isn't one, since a push also needs the company's APNs key; it is kept in memory and written only to the capability's snapshot file in the app's own directory of the store during a session, never to the defaults, another file, the audit log or a log.
- DD-113: dogfood bug reports from the release build, off unless the host enables it. The host makes a `DebugDrawerBugReports` (in `DebugDrawerReceiver`) with the receiver's sessions, optionally the session's `DebugDrawerDiagnosticsCapture` and a closure returning its state as any `Encodable`, enables `.bugReports(_:)`, and calls `trigger(note:)` from a trigger of its own (a shake handler, a menu item): the library binds none. Within a sidecar's session a trigger takes a `Report`: a PNG of the app's own key window, drawn in process (no screen capture), the diagnostics capture's newest lines when a sidecar started it, and the state encoded as JSON, the note and the state redacted by `DebugDrawerDiagnosticsRedaction`; it returns `TriggerResult.captured(_:)` or `.refused(_:)`. Outside a session it returns `.refused(.noActiveSession)` at once, drawing, reading and auditing nothing; in one it meets the receiver's and the capability's gates and, under a grant policy or after `.requiringGrant()`, needs a grant listing the capability, as a sidecar's command does, and is audited as `commandApplied`. Served under `DebugDrawerBugReports.pluginID` (`Snapshot { sessionID, reports, exports, limits }`, `Command.export(id:)`, `delete(id:)`, `deleteAll`); `Limits` (`.standard`: 3 reports, 200 lines, 64 KiB of state, 4 MiB of screenshot) drops the oldest report and leaves out a larger state or screenshot with its size. The app never uploads: `DebugDrawerReceiver` depends on no module, so it links no uploader (modules.py asserts it). `DebugDrawerSidecarKit` gains `DebugDrawerSidecarPlugin.bugReports`, which shows each report with an annotation field, and puts the one picked in Create Report's zip (`Bug Reports/screenshot.png`, `note.txt`, `console.txt`, `state.json`) for Send Report's uploader, sending `export(id:)`. The example host gains Report a Bug (a button and Feedback > Report a Bug), and the example sidecar the Bug Reports plugin.
- DD-112: on-demand diagnostics capture on a release build, off unless the host enables it. The app hands a new `DebugDrawerDiagnosticsCapture` (in `DebugDrawerReceiver`) its log lines (`log(level:message:metadata:subsystem:category:)`) and the requests it sends with their outcome (`record(_:response:body:error:started:)`, after its own call); `receiver.enable(.diagnosticsCapture(capture))` serves them under `DebugDrawerDiagnosticsCapture.pluginID` (`Snapshot { sessionID, lines, requests, dropped, byteCount, limits, exports }`, `Command.start`, `stop`, `export`). Nothing is captured until a sidecar sends `start` in an open session (refused `unknownCapability` while the capability isn't enabled, and `grantMissing` without a grant when made `.requiringGrant()`); until then the calls evaluate none of their arguments, and nothing is ever intercepted: no os_log reading, no URL protocol, no swizzling, so no request is sent again. Each line and request is redacted before it is kept by the new `DebugDrawerDiagnosticsRedaction` (`.standard`: the drawer's credential headers and keys plus `email` and `phone`, a URL's user and password, and value patterns masking email addresses, JWTs, bearer credentials and `password=…` text in messages, metadata, headers, URLs and JSON strings; `adding(headers:keys:jsonPaths:values:)`); only JSON bodies are kept, others left out with their size, and failures keep only their error domain and code. `DebugDrawerDiagnosticsCapture.Limits` bounds a session's capture (`.standard`: 1,000 lines, 200 requests, 64 KiB bodies, 2 MiB in all), oldest first. The capture lives in memory and the capability's snapshot file in the app's own directory of the store, and both are deleted as the sidecar stops it, as the session ends or expires, as a gate turns it off, and, after a kill, as the next launch enables it. A sidecar's report copy is the only one that outlives the session: `export` records it (`Snapshot.exports`, audited `commandApplied`), and `Snapshot.consoleLog` and `networkJSON` are the report's files. The example host and sidecar gain a Diagnostics plugin.
- DD-111: a sidecar can raise the verbosity of chosen subsystems of the app's own logger for its session, on a release build, off unless the host enables it. `receiver.enable(.logLevels(adapter))` serves the subsystems the host's new `DebugDrawerLogLevelAdapter` lists in `elevatableSubsystems()`, each a `DebugDrawerLogSubsystem` (name, the levels a sidecar may set, in the logger's own names, and the level now), through `DebugDrawerLogLevels` (`pluginID`, `Snapshot { subsystems, raisedSubsystems }`, `Command.setLevel(subsystem:level:)`, `reset(subsystem:)`, `resetAll`); the adapter hears each change per subsystem through `setLevel(_:forSubsystem:)` and `resetLevel(forSubsystem:)`. Before it is enabled a command to it is refused as `unknownCapability`; a subsystem the adapter doesn't list is refused as `notExposed`, a level it doesn't list as `malformedCommand`. ### Fixed

- DD-288: reading a Remote Viewing pairing request through accessibility on macOS (VoiceOver, or any app walking the drawer's accessibility tree) no longer can crash the app with a stack overflow. The request's code was selectable text with an accessibility label of its own, which sent SwiftUI's and AppKit's accessibility into a loop; the code is no longer selectable (it is typed on the viewer, not copied) and still reads digit by digit ("Code 1 2 3 4 5 6"). This covers the Sidecar's Mac Viewer too, which shows the same row.
- DD-285: network mocking's URL protocol decides whether it answers a request with rules in effect at under half the instructions and allocations it took. Each rule tried used to work out the request's method, host and path again, and each of its regular expressions bridged a Swift string to an `NSString` anew; the request's are now worked out once, as strings the expressions read without bridging. Which requests a rule matches is unchanged. The Network plugin's own mock rules match the same way.
- DD-282: a screen recording no longer can crash the app in CoreVideo as it draws a frame. Each movie's frames come from a pixel buffer pool the recorder makes and holds itself, where they used to come from AVFoundation's pixel buffer adaptor, which replaces its pool on its own queue about eight frames into every movie, and again as the encoder fails, while the next frame might be drawn from the pool it released.
- DD-281: the View Inspector's grid no longer keeps a `.debugGrid()` view's probe alive after the view is removed. The controller's weak table of probes autoreleased them as they were added or listed, so a removed probe lived on until the main run loop's autorelease pool drained. The probes are now held by Swift weak references, which autorelease nothing, so a probe is freed and no longer listed the moment its last owner lets go.
- DD-268: the Console masks what it copies and reports by the drawer's redaction rules, where it used to copy and report every line as logged. Copy All, a line's new Copy Line (its context menu, or its edit menu on iOS) and the bug report's `console.txt` and `console-previous.txt` mask a metadata field whose key contains a key pattern (`token=[REDACTED]`), and the value of each `key=value` or `key: value` pair in a line's text whose key does, quoted JSON-style pairs and URL query items included. Copy All and Copy Line follow the rules of the drawer the Console is shown in. With `.none` the copies and the report are as before. `DebugDrawerRedaction.redacting(text:)` is new; the diagnostics capture (`DebugDrawerDiagnosticsRedaction`) masks such pairs in the text it keeps by the same reading, before its value patterns.
- DD-267: a session-scoped change no longer outlives a session the app was killed or quit during. The receiver records, in the app's directory of the store (`unreverted-changes.json`), each session-scoped capability a session changed, before the change is applied, and clears it once the change is reverted; as the next launch enables that capability, it performs the scope's revert command and audits it as `changeReverted` in the session that made the change. Tweaks enabled with `scope: .session(revertWith: .resetAll)` are now reset after a kill, and so is a model of the app's own enabled with `.model(_:id:scope:)` and a session scope. A capability the next launch doesn't enable keeps its record until a launch does. A session that ended leaves nothing to revert, and the capabilities that already revert their own leftovers as they are made (feature flags, experiments, log levels, environments, location, UserDefaults) are reverted once, as before.
- DD-266: `DebugDrawerSidecarView` no longer cuts plugin names short ("Acce…", "Metri…") when an app serves many plugins. At compact width (an iPhone, an iPad in a narrow split) an app's screen is a list, as on the watch: its version and channel, its session, a row per plugin that opens the plugin under its name, and Create Report. At regular width (an iPad, a Mac window) the plugins stay a segmented picker while every name fits in full, and become a pop-up menu of the plugins, naming the one shown, when they don't; the picker now marks the plugin shown before one is picked.
- DD-253: on iOS a context menu opened in the drawer's panel (a section header's Show Alone, Pin, Silence Notices) closes on a tap beside a regular-width panel, and that tap no longer reaches the app; the next touch and hold opens the menu again rather than only closing the last one. While the menu, or a sheet or popover from the panel, shows, the drawer's window takes every touch, so its items past the panel's edge can be chosen too; with none showing, taps beside the panel reach the app as before.
- DD-250: stopping a screen recording no longer can crash the app when the movie's encoder fails on its own (a disk filling up, media services reset) at that moment. The movie still runs from the first frame to one frame after the last frame written; a last frame the encoder wasn't ready for at Stop is left out, and the movie ends one frame after the frame before it, where it used to run on to that frame's time.
- DD-279: a `DebugDrawer()` of your own is freed as soon as its last owner lets it go. The weak tables core kept of every drawer (for a plugin's badges and toasts) and of the drawers a store's badge shows in autoreleased the drawers as they were added or listed, so a drawer could outlive its owner until the main run loop's autorelease pool drained (seen on the tvOS simulator). They now hold Swift weak references, which autorelease nothing.
- DD-278: Analytics masks event properties, on screen, in Copy JSON and in Export All, by the redaction rules of the drawer it is shown in, rather than always `DebugDrawer.shared`'s: installed in a `DebugDrawer(defaults:)` of your own, it follows that drawer's rules as they change and ignores the shared drawer's. Drawn outside any drawer it still uses `DebugDrawer.shared`'s.
- DD-280: Cookies, Keychain, UserDefaults, Notifications and Network mask what they show, copy and export by the redaction rules of the drawer they are shown in, rather than always `DebugDrawer.shared`'s: shown in a `DebugDrawer(defaults:)` of your own, each follows that drawer's rules as they change. Network also writes each request and WebSocket connection to its session on disk masked by the rules of the drawer that installed the plugin over its store last (the one its requests go to), and by `DebugDrawer.shared`'s while no drawer holds it. `DebugDrawerReportContributor`'s documentation now says a report is masked by the rules of the drawer writing it.
- DD-276: Analytics, Crash Reports, Hangs, Leaks and MetricKit badge the drawers that installed them, rather than always `DebugDrawer.shared`, as their counts change: one installed only in a `DebugDrawer()` of your own badges that drawer and leaves `shared` alone. A drawer shows the count as it installs the plugin and clears it as it removes it, and a count that changes while no drawer holds the plugin badges none. Installed through `install(...)` into `shared`, they badge it as before.
- DD-275: a plugin's `setBadge(_:)`, `clearBadge()` and `postToast(_:)` reach the drawers that hold the plugin, globally or locally, rather than always `DebugDrawer.shared`: a plugin installed in a `DebugDrawer()` of your own badges and toasts that drawer, one in two drawers reaches both, and one no drawer holds yet still posts to `shared`.
- DD-173: the hang monitor (the Hangs plugin's and `PerformanceTraces`') no longer reports a stall while the app is out of sight as a hang. On iOS that is from resigning active until it is active again (the deactivation, the background, the app switcher's snapshot, the return to the foreground); a stall the app resigns active in is dropped whole, and one in the app's own code once it is active again still counts, from becoming active, with its stack. On the Mac an inactive app is still on screen and keeps counting; only a hidden Mac app, and a Mac Catalyst app in the background, doesn't.
- DD-273: on the Mac, closing a window detaches its panel from the drawer that attached it, rather than from `DebugDrawer.shared`, so a `DebugDrawer()` of your own no longer keeps a closed window's attachment, and the shared drawer keeps the local plugins of a window another drawer attached.
- DD-270: under a `DebugDrawerGrantPolicy`, `AnalyticsEventsMirror` and `MetricKitPayloadsMirror` serve only a session whose grant lists their capability (`AnalyticsEventsMirror.pluginID`, `MetricKitPayloadsMirror.pluginID`), as `PushRegistrationMirror` and `DebugDrawerAppState` do. A session whose grant doesn't list it is served its ID and no events or payloads, and the analytics mirror keeps nothing recorded during it. Before, a grant meant for another capability also exposed the app's analytics events and MetricKit payloads. Without a grant policy nothing changes. The security article's table and the README describe the new behaviour.
- DD-269: `DebugDrawerSidecarConnection.host(_:)` finds a plugin it hosted by the `DebugDrawerSidecarPlugin.id` it was asked for, so hosting one again returns the first and keeps one copy (concurrent calls too), and Create Report holds its contribution once, whatever the made plugin's own `id` is. Before, a plugin keeping its type's default `id` (as `Example/Sidecar`'s capability plugins do) was hosted again on every call and contributed to the report once per copy. The kit's Bug Reports plugin no longer sets its `id` to the capability's to work around it.

- DD-110: tweaks declared `.productionSafe()` can be changed from a sidecar app in a release build. `DebugDrawerTweaks`, a new UI-free library a release build links beside the receiver, holds `Tweak`, `TweakStoredValue` (now `Codable` as the bare JSON value), `TweakStorage`, `UserDefaultsTweakStorage`, the now public `TweakControl` and `TweakOption`, and the typed accessors; `DebugDrawerTweaksPlugin` re-exports it, so `import DebugDrawerTweaksPlugin` sees them unchanged. `receiver.enable(.tweaks(AppTweaks.backend, ...))` serves a sidecar the production-safe tweaks alone through `TweaksModel` (`pluginID`, `Snapshot`, `Command.setValue`/`reset`/`resetAll`): a command naming any other tweak is refused as the new `DebugDrawerAuditEntry.Refusal.notExposed`, and a value that isn't one of the tweak's as `malformedCommand`, inside a session too. - DD-124: a release build can mirror the analytics events it records to a sidecar during a session, redacted in the app. `DebugDrawerAnalytics`, a new UI-free library a release build links beside the receiver, holds `AnalyticsEvents` (`record` and `defaultCapacity`) and `AnalyticsValue` (now `Codable`); `DebugDrawerAnalyticsPlugin` re-exports it and keeps `install(capacity:)`, so `import DebugDrawerAnalyticsPlugin` sees them unchanged. `receiver.enable(.analyticsEvents(sessions:redaction:capacity:))`, off unless enabled, serves `AnalyticsEventsMirror` (`pluginID`, `Snapshot` of the open session's ID and its events, `Command.clear`): only events recorded while a session is open reach the sidecar, in order, none from before it and none after it ends or expires. - DD-114: a release build can forward the crash reports and other MetricKit payloads it receives to a sidecar, so dogfooders' crashes reach the team without a crash SDK. `DebugDrawerMetricKit`, a new UI-free library a release build links beside the receiver, holds `MetricKitPayloadKind` and the `MXMetricManager` subscriber; `DebugDrawerMetricKitPlugin` re-exports it, so `import DebugDrawerMetricKitPlugin` sees `MetricKitPayloadKind` unchanged. `receiver.enable(.metricKitPayloads(sessions:directory:redaction:capacity:))`, off unless enabled, subscribes to MetricKit alone (no signal or exception handler in release) and keeps each payload, crash diagnostics among them, redacted by `MetricKitRedaction` (`.standard` masks an Objective-C exception's `composedMessage` and `arguments`) in the app's own Application Support directory across launches, the newest ten, none over a megabyte; `MetricKitPayloadsMirror` (`pluginID`, `Snapshot` of the open session's ID and the payloads, `Command.delete(id:)` and `deleteAll`) serves them only while a session is open, so a crash delivered at the next launch reaches the next session.
- DD-92: `DebugDrawerReceiver`, a new library and the only DebugDrawer code a release build may link: UI-less, with no interception and no dependency on the drawer. `DebugDrawerReceiver(directory:sessions:)` serves a sidecar app, over the app group's store the sidecar transports already read, only the capabilities the host passes to `enable(_:)` (`.featureFlagOverrides(_:)` over a `DebugDrawerFeatureFlagAdapter`, through the `DebugDrawerFeatureFlagOverrides` model, or `.model(_:id:scope:)` for any `DebugDrawerPluginModel`), within `DebugDrawerSessions` the sidecar opens; a command to a capability not enabled, any command while none is, and any command outside a session is refused, logged and audited, and `disable(_:)` takes one back. `DebugDrawerPluginModel`, `DebugDrawerSessions`, `DebugDrawerSessionState`, `DebugDrawerChangeScope` and `DebugDrawerAuditEntry` move to that module, which `DebugDrawer` re-exports, so `import DebugDrawer` sees them unchanged; the sessions are now real in release builds too, where only a receiver opens one. A new macOS example, `ExampleApp_macOSReceiver`, links the receiver alone.
- DD-96: `DebugDrawerBackgroundKeeper` keeps an app reachable by its sidecar in the background while a session is open, through only what each platform sanctions, and ends every request as the session ends or expires: a UIKit background task on iOS, iPadOS, tvOS and visionOS (asked for again as the app returns to the foreground), a `BGContinuedProcessingTask` with the system's progress UI on iOS and iPadOS 26 and later from `startSession(duration:title:subtitle:)`, a person's action (identifier `<prefix>.<session ID>`, the prefix listed as `<prefix>.*` in `BGTaskSchedulerPermittedIdentifiers`, falling back to the background task when unavailable or refused), and a `ProcessInfo` activity against App Nap on macOS and Mac Catalyst; nothing on watchOS, and no background mode claimed. `request` publishes what it holds as a `DebugDrawerBackgroundRequest`. The README's "Sidecar sessions in the background" lists each platform's limits.
- DD-105: a sidecar's transports fail closed when the system refuses an app group's container. `DebugDrawerSocketServer.start()`, `DebugDrawerAppGroupStoreServer.start()` and the socket, store and sidecar transports' initializers throw the new `DebugDrawerTransportError.accessDenied` when the sandbox, a declined macOS prompt or the files' modes refuse their directory or socket (EACCES or EPERM), checking before they write, and write nothing anywhere; a sidecar refused only the socket publishes it in the new `DebugDrawerSidecarTransport.socketError` and reads the store. `DebugDrawerAppGroupContainer(groupIdentifier:)` resolves the group's container the same way for sandboxed and non-sandboxed apps, with the socket at `DebugDrawer/drawer.sock` and the store in `DebugDrawer/`, and throws the new `noAppGroupContainer` where the system gives none. `DebugDrawerTransportError` is now a `LocalizedError` whose descriptions say what to fix; the socket server makes its socket's directory if it doesn't exist. The README and Writing Global and Local Plugins say which entitlements and signing keep macOS from asking, and what a refusal looks like.
- DD-98: sidecar sessions. `DebugDrawerModelRegistry(sessions:)` takes a `DebugDrawerSessions`, and then performs a command a transport carries in only while a session the sidecar opened is active, and only on a model registered with `register(_:id:scope:)` and a `DebugDrawerChangeScope`; anything else is refused. A sidecar opens and ends a session through the sessions' own model (`DebugDrawerSessions.pluginID`, `DebugDrawerSessionCommand`, `DebugDrawerSessionState`). Sessions expire, at most the host's `maximumDuration` after they open; ending or expiry reverts `.session(revertWith:)` changes and keeps `.persistent` ones. The sessions publish their state for the host to draw its own indicator, and keep a bounded audit log of `DebugDrawerAuditEntry` values (date, session, capability, event, never a command's contents), publishing each for the host to forward. Release builds get stand-ins that never open a session.
- DD-95: `DebugDrawerSidecarTransport`, the transport for a sidecar app, reads the app over its Unix domain socket while the app answers on it and through its app-group store while it doesn't, and switches each way on its own: when the socket goes it reads the store, and when the app makes the socket again it goes back, learning of both from events (the stream's end, a dispatch source on the socket's directory). No command is lost or performed twice across either switch, in the order sent: over the socket each command is kept until the app acknowledges it (the new `acknowledgements` capability and `acknowledgement` message, each command now carrying a `commandID`), what wasn't acknowledged is left in the store, and the app performs a command ID once; commands still waiting in the store when the socket returns go over it first. A socket's path may now be longer than the 103 bytes its address holds, as an app group's container is in the iOS simulator: the socket servers and transports bind and connect to it by its file name from its directory, and throw `socketPathTooLong` only for a file name that long.
- DD-94: the app-group store survives either app being suspended, quitting or being killed. `DebugDrawerAppGroupStoreServer` performs the commands waiting in the store as the app comes back to the foreground, as well as when it starts and as each lands; a process killed mid-write leaves the last complete snapshot or command readable, and the cut-off file is never read; the store is bounded: the server removes cut-off snapshot files as it starts, and the commands waiting are capped at 256 files and 16 MiB, the oldest removed first, with no command larger left.
- DD-97: the transports to a sidecar, a socket viewer, an app-group store reader and a remote viewer work across releases. Each side of the socket and network transports says hello as it connects, naming the protocol's major version it speaks, the oldest it still speaks and its capabilities (`commands`, `unsubscribe`); builds one major version apart connect and use only the capabilities both list, and builds two apart are closed, their connects throwing the new `DebugDrawerTransportError.incompatibleVersion`. A message of a kind a build doesn't know is dropped and logged once per kind, and the connection stays up. The app-group store's files carry a schema version and the writer's version, and older ones are migrated forward as they are read. A viewer now tells the app when it releases a plugin's last transport, and the app stops sending that plugin's snapshots.
- DD-228: `installNetwork(bypassing:)` keeps the hosts an app names, and their subdomains, out of the Network plugin, so an app that pins certificates can install it for the rest of its traffic: their requests never reach the URL protocol, go out on the app's own session with its own delegate, and aren't logged, mocked, conditioned or recorded as WebSockets; text that isn't a host traps. - DD-209: `DebugDrawer.registerLocal(_:in:)` ties a local plugin to one `NSWindow` (macOS) or `UIWindowScene` (iOS, Mac Catalyst and visionOS), so a UIKit- or AppKit-only app can list a plugin in only that window's drawer, as `debugLocalPlugin(_:)` does for a SwiftUI view. - DD-210: plugins get an optional lifecycle, and drawers can be made apart from `DebugDrawer.shared`. `DebugDrawerPlugin` adds `install(in:)`, `uninstall(from:)`, `didBecomeVisible(in:)` and `didBecomeHidden(in:)`, each doing nothing by default: a drawer installs a plugin as it registers it, uninstalls it as `unregisterGlobal(id:)` or its view's disappearance removes it, and reports it visible while its section's body, its view shown alone or its HUD readout is on screen. `DebugDrawer()` and `DebugDrawer(defaults:)` make a drawer that owns plugins of its own, so two coexist in one process; release builds get stand-ins of both.
- DD-212: every shipped plugin can be uninstalled: `unregisterGlobal(id:)` stops what it started and lets go of what it captured, once no drawer holds it. Network unregisters its URL protocol and, with Disk I/O, Location and View Inspector, gives every swizzled method its original implementation back; Accessibility clears its overrides; Crash Reports restores the signal and exception handlers it replaced. What a plugin saved stays for the next install, and installing again works. `NetworkStore.uninstall()`, `DiskIOStore.uninstall()` and `ConsoleLogStore.uninstall()` undo their `install()`.
- DD-91: a plugin's data can be read and driven apart from its view. `DebugDrawerPluginModel`, an optional protocol, is a plugin's model without SwiftUI types: a `Codable` snapshot of everything its view shows, and `Codable` commands that change it. `DebugDrawerPluginTransport` joins a view to a model: `direct(to:)` in the process, where a command lands before `send(_:)` returns, and `init(initial:snapshots:send:)` from a stream of snapshots and a closure for commands, for a model elsewhere; `snapshots()` hands the changes out as a stream. - DD-89: the plugin-authoring guide (Writing Global and Local Plugins, "Intercepting the app's calls") states the contract an interception plugin keeps: install is idempotent, uninstall restores exactly what install changed, the app sees the same results, capture is bounded and the drawer's own activity is left out. - DD-93: a plugin's model can be read and driven from another process. `DebugDrawerTransport` is one protocol a viewer holds, chosen per connection at run time, that hands out the `DebugDrawerPluginTransport` a plugin's view already draws from: `DebugDrawerInProcessTransport` in the app's own process, `DebugDrawerSocketTransport` over a Unix domain socket while the app runs, and `DebugDrawerAppGroupStoreTransport` from a shared directory, such as an app group's container, that keeps the last snapshots and queues commands while the app is suspended.
