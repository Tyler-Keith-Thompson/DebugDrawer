# Changelog

Notable changes in each release, newest first, in the style of
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/). Work lands under Unreleased; before
`just deploy`, rename that heading to the new version and date (`## [0.1.2] - 2026-11-17`), start a
new empty Unreleased above it, and commit. Deploy refuses to tag a version with no entry here, and
the entry becomes the GitHub release's notes.

## [Unreleased]

### Added

- DD-103: an example sidecar and the production host it drives, on iOS and the Mac. `Example/Receiver` (formerly the Mac-only `ExampleApp_macOSReceiver`, now `ExampleApp_Receiver_macOS` and `ExampleApp_Receiver_iOS`) links only the receiver and the capability modules and serves every capability the library ships (feature flag overrides, production-safe tweaks, localization review, accessibility overrides, analytics events, MetricKit payloads, network mocking) within sessions that need a grant, with its own session indicator, a background keeper and a kill switch; each capability has something in the host that changes as the sidecar acts. `Example/Sidecar` adds a plugin for each capability through `DebugDrawerSidecarPlugin(id:title:icon:snapshot:command:plugin:)` and signs grants with RFC 8037's published test key. `just run sidecar` launches the pair in the iOS simulator, `just run sidecar macOS` on the Mac, where `scripts/sign_example.py --app-group` signs both into the signing team's app group (ad hoc, they share a folder in Caches). The README's "The example pair" says what to try.

- DD-106: the sidecar's transports are tested on tvOS and watchOS as well as visionOS and Mac Catalyst: core's tests now run in the tvOS and watchOS simulators under `just test` (`DebugDrawerTests_tvOS`, `DebugDrawerTests_watchOS`) and `just spm-test` (`just spm-tvos-test`, `just spm-watchos-test`). The README's new "The sidecar on Apple TV, Vision Pro, Apple Watch and Mac Catalyst" section says how each platform reaches its sidecar; on watchOS the sidecar is a watch app on the same watch, sharing the watch's app group, not a WatchConnectivity relay through the iPhone.
- DD-121: a sidecar can mock and condition responses on a release build, for a session whose grant lists it, off unless the host enables it. `DebugDrawerNetwork`, a new library a release build links beside the receiver, holds `NetworkMockRule` and `NetworkConditionProfile` (moved from the Network plugin, which re-exports it) and `NetworkMocking`: the host makes it with the hosts a sidecar may mock (`NetworkMocking.AllowedHost`, `.exact(_:)` or `.domain(_:)`; an empty list mocks nothing), enables `.networkMocking(_:)`, which requires a grant, and lists `NetworkMockingURLProtocol` in the `URLSessionConfiguration`s whose requests may be mocked; nothing is registered globally and no method is replaced, so `URLSession.shared` and every other session are never touched. `NetworkMocking.Command` sets the session's rules and profiles (`setRules(_:)`, `setConditions(_:)`, `reset`); a rule answers a request to an allowed host while the session is open and unexpired, delayed, paced or failed by the first matching profile; regular expressions and file bodies are refused as `malformedCommand`. Each session starts with none, and they clear as it ends, expires or a gate turns off. `snapshot.isActive` tells the host to show that mocking is active.
- DD-101: `DebugDrawerSidecarKit`, a new library a company builds its own sidecar app from (iOS, iPadOS and macOS, debug builds; release builds get stand-ins). `DebugDrawerSidecarView(groupIdentifier:plugins:sessionDuration:grant:)` is the whole app: it lists the apps in the group serving a sidecar (`DebugDrawerReceiver` and `DebugDrawerAppGroupStoreServer` now write a presence file, `<store>/presence/<bundle ID>.json`, as they start, and remove it as they stop; an app whose receiver is gated off is listed as turned off), opens and ends their sessions, fetching a grant through `grant` when given, hosts their Console and Network (`ConsolePlugin(transport:)` and `NetworkPlugin(transport:)`, new) and any `DebugDrawerSidecarPlugin` over the socket or the store, and creates and uploads a report of them. `DebugDrawerSidecarAppList`, `DebugDrawerSidecarConnection`, `DebugDrawerSidecarApp` and `DebugDrawerSidecarPlugin` are its parts, for a layout of the app's own. `Example/Sidecar` is the example's sidecar app (`just run sidecar`).
- DD-100: the company can turn the release-build receiver off for everyone without an app release, through a gate the host backs with its own remote configuration. `DebugDrawerReceiver.isAllowed` (or `init(directory:sessions:isAllowed:)`), asked before anything else at every command: while it returns `false` every command, a session's opening included, is refused as the new `DebugDrawerAuditEntry.Refusal.receiverDisabled`, the open session ends as the new `Ending.disabledByHost`, reverting its session-scoped changes, and no capability's snapshot is served. `enable(_:isAllowed:)` gates one capability: its commands are refused as `capabilityDisabled`, its snapshot leaves the store and its session-scoped change reverts at once, while the session and the other capabilities go on. The receiver asks the gates at each command, at start, as the app comes to the foreground and before writing a snapshot, and `reevaluateGates()`, which the host calls as its configuration updates, ends an open session with no command needed.
- DD-99: optional signed, expiring grants for sidecar sessions. `DebugDrawerSessions(maximumDuration:auditCapacity:grantPolicy:)` takes a `DebugDrawerGrantPolicy` (a verifier, the app's audience and a clock-skew tolerance for `notBefore`); with one, a session opens only with a grant the sidecar sends in `DebugDrawerSessionCommand.open(duration:grant:)` that verifies, is for this app, is valid now and hasn't opened a session before, lasts no longer than the grant, and applies only commands to the capabilities it lists, refusing and auditing the rest with the new `grantMissing`, `grantInvalid`, `grantWrongAudience`, `grantNotYetValid`, `grantExpired`, `grantReplayed` and `capabilityNotGranted`. `DebugDrawerSignedGrantVerifier` verifies DebugDrawer's format, a JSON Web Token signed with Ed25519 (`EdDSA`) or P-256 (`ES256`) by keys the app embeds (`DebugDrawerGrantPublicKey`); `DebugDrawerGrantVerifier` lets a host bring its own. `DebugDrawerSession.grant` and `sessionOpened(expires:grant:)` name the grant by ID and subject, never its token. `DebugDrawerReceiverCapability.requiringGrant()` marks a capability that needs a grant even without a policy. Without a policy, sessions work as before. The README's "Signed grants" documents the format and a test signer.
- DD-123: translators and accessibility reviewers can work on a release build from a sidecar, for the session, off unless the host enables it. `DebugDrawerLocalization`, a new library a release build links beside the receiver, holds `Localization` and its `Mode` (now `Codable`) and `LocalizationReview`: the host reads strings through `localizedString(forKey:value:table:bundle:)` or `localizedString(_:)` (a `LocalizedStringResource`, resolved with its arguments and plural first), and `receiver.enable(.localizationReview())` lets a sidecar set `LocalizationReview.Command.setMode(_:)` to `showingKeys` or `pseudoLocalized` within a session, with nothing intercepted; `.localizationReview()` redraws the root view as the mode changes. `DebugDrawerAccessibility`, another, holds `AccessibilityEnvironmentOverrides`: `receiver.enable(.accessibilityEnvironmentOverrides())` lets a sidecar override Dynamic Type, Increase Contrast and Reduce Motion within a session, and the `.accessibilityEnvironmentOverrides()` modifier on the root view applies them to its SwiftUI views. Both revert as the session ends or expires. `DebugDrawerLocalizationPlugin` and `DebugDrawerAccessibilityPlugin` re-export them, and `Localization.install(mode:)` is unchanged.
- DD-110: tweaks declared `.productionSafe()` can be changed from a sidecar app in a release build. `DebugDrawerTweaks`, a new UI-free library a release build links beside the receiver, holds `Tweak`, `TweakStoredValue` (now `Codable` as the bare JSON value), `TweakStorage`, `UserDefaultsTweakStorage`, the now public `TweakControl` and `TweakOption`, and the typed accessors; `DebugDrawerTweaksPlugin` re-exports it, so `import DebugDrawerTweaksPlugin` sees them unchanged. `receiver.enable(.tweaks(AppTweaks.backend, ...))` serves a sidecar the production-safe tweaks alone through `TweaksModel` (`pluginID`, `Snapshot`, `Command.setValue`/`reset`/`resetAll`): a command naming any other tweak is refused as the new `DebugDrawerAuditEntry.Refusal.notExposed`, and a value that isn't one of the tweak's as `malformedCommand`, inside a session too. Changes persist in the tweaks' storage (scope `.persistent` by default, or `.session(revertWith: .resetAll)`) and reach `Tweak.value` and `publisher`; in release a production-safe tweak reads its stored value once the app has made the capability, and every other tweak reads its default as before. The receiver example offers a tweak too.
- DD-124: a release build can mirror the analytics events it records to a sidecar during a session, redacted in the app. `DebugDrawerAnalytics`, a new UI-free library a release build links beside the receiver, holds `AnalyticsEvents` (`record` and `defaultCapacity`) and `AnalyticsValue` (now `Codable`); `DebugDrawerAnalyticsPlugin` re-exports it and keeps `install(capacity:)`, so `import DebugDrawerAnalyticsPlugin` sees them unchanged. `receiver.enable(.analyticsEvents(sessions:redaction:capacity:))`, off unless enabled, serves `AnalyticsEventsMirror` (`pluginID`, `Snapshot` of the open session's ID and its events, `Command.clear`): only events recorded while a session is open reach the sidecar, in order, none from before it and none after it ends or expires. Each is redacted by `AnalyticsRedaction` on the recording thread before it is kept, so no unredacted value reaches the snapshot, the store's files or the audit log: `.standard` masks keys containing email, phone, token, secret, password, session, auth or API key and values holding an email address or a JSON Web Token, and `adding(keys:values:)` adds the host's own key substrings and regular expressions. While no session mirrors, `record` in release still evaluates none of its arguments.
- DD-114: a release build can forward the crash reports and other MetricKit payloads it receives to a sidecar, so dogfooders' crashes reach the team without a crash SDK. `DebugDrawerMetricKit`, a new UI-free library a release build links beside the receiver, holds `MetricKitPayloadKind` and the `MXMetricManager` subscriber; `DebugDrawerMetricKitPlugin` re-exports it, so `import DebugDrawerMetricKitPlugin` sees `MetricKitPayloadKind` unchanged. `receiver.enable(.metricKitPayloads(sessions:directory:redaction:capacity:))`, off unless enabled, subscribes to MetricKit alone (no signal or exception handler in release) and keeps each payload, crash diagnostics among them, redacted by `MetricKitRedaction` (`.standard` masks an Objective-C exception's `composedMessage` and `arguments`) in the app's own Application Support directory across launches, the newest ten, none over a megabyte; `MetricKitPayloadsMirror` (`pluginID`, `Snapshot` of the open session's ID and the payloads, `Command.delete(id:)` and `deleteAll`) serves them only while a session is open, so a crash delivered at the next launch reaches the next session.
- DD-92: `DebugDrawerReceiver`, a new library and the only DebugDrawer code a release build may link: UI-less, with no interception and no dependency on the drawer. `DebugDrawerReceiver(directory:sessions:)` serves a sidecar app, over the app group's store the sidecar transports already read, only the capabilities the host passes to `enable(_:)` (`.featureFlagOverrides(_:)` over a `DebugDrawerFeatureFlagAdapter`, through the `DebugDrawerFeatureFlagOverrides` model, or `.model(_:id:scope:)` for any `DebugDrawerPluginModel`), within `DebugDrawerSessions` the sidecar opens; a command to a capability not enabled, any command while none is, and any command outside a session is refused, logged and audited, and `disable(_:)` takes one back. `DebugDrawerPluginModel`, `DebugDrawerSessions`, `DebugDrawerSessionState`, `DebugDrawerChangeScope` and `DebugDrawerAuditEntry` move to that module, which `DebugDrawer` re-exports, so `import DebugDrawer` sees them unchanged; the sessions are now real in release builds too, where only a receiver opens one. A new macOS example, `ExampleApp_macOSReceiver`, links the receiver alone.
- DD-96: `DebugDrawerBackgroundKeeper` keeps an app reachable by its sidecar in the background while a session is open, through only what each platform sanctions, and ends every request as the session ends or expires: a UIKit background task on iOS, iPadOS, tvOS and visionOS (asked for again as the app returns to the foreground), a `BGContinuedProcessingTask` with the system's progress UI on iOS and iPadOS 26 and later from `startSession(duration:title:subtitle:)`, a person's action (identifier `<prefix>.<session ID>`, the prefix listed as `<prefix>.*` in `BGTaskSchedulerPermittedIdentifiers`, falling back to the background task when unavailable or refused), and a `ProcessInfo` activity against App Nap on macOS and Mac Catalyst; nothing on watchOS, and no background mode claimed. `request` publishes what it holds as a `DebugDrawerBackgroundRequest`. The session ends when the last sidecar disconnects from the socket, now published by `DebugDrawerSocketServer.viewerDisconnections` beside `viewerCount`, and when the person stops the continued processing task. It is part of `DebugDrawerReceiver` and works in every build, so a release build's receiver keeps its app reachable the same way; core adds `init(sessions:socketServer:continuedProcessingIdentifierPrefix:)`. The README's "Sidecar sessions in the background" lists each platform's limits.
- DD-105: a sidecar's transports fail closed when the system refuses an app group's container. `DebugDrawerSocketServer.start()`, `DebugDrawerAppGroupStoreServer.start()` and the socket, store and sidecar transports' initializers throw the new `DebugDrawerTransportError.accessDenied` when the sandbox, a declined macOS prompt or the files' modes refuse their directory or socket (EACCES or EPERM), checking before they write, and write nothing anywhere; a sidecar refused only the socket publishes it in the new `DebugDrawerSidecarTransport.socketError` and reads the store. `DebugDrawerAppGroupContainer(groupIdentifier:)` resolves the group's container the same way for sandboxed and non-sandboxed apps, with the socket at `DebugDrawer/drawer.sock` and the store in `DebugDrawer/`, and throws the new `noAppGroupContainer` where the system gives none. `DebugDrawerTransportError` is now a `LocalizedError` whose descriptions say what to fix; the socket server makes its socket's directory if it doesn't exist. The README and Writing Global and Local Plugins say which entitlements and signing keep macOS from asking, and what a refusal looks like.
- DD-98: sidecar sessions. `DebugDrawerModelRegistry(sessions:)` takes a `DebugDrawerSessions`, and then performs a command a transport carries in only while a session the sidecar opened is active, and only on a model registered with `register(_:id:scope:)` and a `DebugDrawerChangeScope`; anything else is refused. A sidecar opens and ends a session through the sessions' own model (`DebugDrawerSessions.pluginID`, `DebugDrawerSessionCommand`, `DebugDrawerSessionState`). Sessions expire, at most the host's `maximumDuration` after they open; ending or expiry reverts `.session(revertWith:)` changes and keeps `.persistent` ones. The sessions publish their state for the host to draw its own indicator, and keep a bounded audit log of `DebugDrawerAuditEntry` values (date, session, capability, event, never a command's contents), publishing each for the host to forward. Release builds get stand-ins that never open a session.
- DD-95: `DebugDrawerSidecarTransport`, the transport for a sidecar app, reads the app over its Unix domain socket while the app answers on it and through its app-group store while it doesn't, and switches each way on its own: when the socket goes it reads the store, and when the app makes the socket again it goes back, learning of both from events (the stream's end, a dispatch source on the socket's directory). No command is lost or performed twice across either switch, in the order sent: over the socket each command is kept until the app acknowledges it (the new `acknowledgements` capability and `acknowledgement` message, each command now carrying a `commandID`), what wasn't acknowledged is left in the store, and the app performs a command ID once; commands still waiting in the store when the socket returns go over it first. A socket's path may now be longer than the 103 bytes its address holds, as an app group's container is in the iOS simulator: the socket servers and transports bind and connect to it by its file name from its directory, and throw `socketPathTooLong` only for a file name that long.
- DD-94: the app-group store survives either app being suspended, quitting or being killed. `DebugDrawerAppGroupStoreServer` performs the commands waiting in the store as the app comes back to the foreground, as well as when it starts and as each lands; a process killed mid-write leaves the last complete snapshot or command readable, and the cut-off file is never read; the store is bounded: the server removes cut-off snapshot files as it starts, and the commands waiting are capped at 256 files and 16 MiB, the oldest removed first, with no command larger left.
- DD-97: the transports to a sidecar, a socket viewer, an app-group store reader and a remote viewer work across releases. Each side of the socket and network transports says hello as it connects, naming the protocol's major version it speaks, the oldest it still speaks and its capabilities (`commands`, `unsubscribe`); builds one major version apart connect and use only the capabilities both list, and builds two apart are closed, their connects throwing the new `DebugDrawerTransportError.incompatibleVersion`. A message of a kind a build doesn't know is dropped and logged once per kind, and the connection stays up. The app-group store's files carry a schema version and the writer's version, and older ones are migrated forward as they are read. A viewer now tells the app when it releases a plugin's last transport, and the app stops sending that plugin's snapshots.
- DD-228: `installNetwork(bypassing:)` keeps the hosts an app names, and their subdomains, out of the Network plugin, so an app that pins certificates can install it for the rest of its traffic: their requests never reach the URL protocol, go out on the app's own session with its own delegate, and aren't logged, mocked, conditioned or recorded as WebSockets; text that isn't a host traps. The README's new "Network: apps that pin certificates" says what the plugin guarantees such an app (the app's delegate decides every TLS challenge, a refused pin sends no request line or headers, a session made before `installNetwork()` still asks its delegate, a stream held open passes through with its stored body capped) and what isn't tested (ATS `NSPinnedDomains`, pinning libraries).
- DD-209: `DebugDrawer.registerLocal(_:in:)` ties a local plugin to one `NSWindow` (macOS) or `UIWindowScene` (iOS, Mac Catalyst and visionOS), so a UIKit- or AppKit-only app can list a plugin in only that window's drawer, as `debugLocalPlugin(_:)` does for a SwiftUI view. It returns the token `unregisterLocal(id:token:)` takes, closing the window or disconnecting the scene removes the registration, and release builds get a stand-in that drops the plugin.
- DD-210: plugins get an optional lifecycle, and drawers can be made apart from `DebugDrawer.shared`. `DebugDrawerPlugin` adds `install(in:)`, `uninstall(from:)`, `didBecomeVisible(in:)` and `didBecomeHidden(in:)`, each doing nothing by default: a drawer installs a plugin as it registers it, uninstalls it as `unregisterGlobal(id:)` or its view's disappearance removes it, and reports it visible while its section's body, its view shown alone or its HUD readout is on screen. `DebugDrawer()` and `DebugDrawer(defaults:)` make a drawer that owns plugins of its own, so two coexist in one process; release builds get stand-ins of both.
- DD-212: every shipped plugin can be uninstalled: `unregisterGlobal(id:)` stops what it started and lets go of what it captured, once no drawer holds it. Network unregisters its URL protocol and, with Disk I/O, Location and View Inspector, gives every swizzled method its original implementation back; Accessibility clears its overrides; Crash Reports restores the signal and exception handlers it replaced. What a plugin saved stays for the next install, and installing again works. `NetworkStore.uninstall()`, `DiskIOStore.uninstall()` and `ConsoleLogStore.uninstall()` undo their `install()`.
- DD-91: a plugin's data can be read and driven apart from its view. `DebugDrawerPluginModel`, an optional protocol, is a plugin's model without SwiftUI types: a `Codable` snapshot of everything its view shows, and `Codable` commands that change it. `DebugDrawerPluginTransport` joins a view to a model: `direct(to:)` in the process, where a command lands before `send(_:)` returns, and `init(initial:snapshots:send:)` from a stream of snapshots and a closure for commands, for a model elsewhere; `snapshots()` hands the changes out as a stream. Network and Console are built this way, through `NetworkModel` and `ConsoleModel` with their `NetworkSnapshot`, `NetworkCommand`, `ConsoleSnapshot` and `ConsoleCommand`; `NetworkEntry`, `NetworkTimingMetrics`, `NetworkConditionEffect`, `NetworkStore.StatusFilter` and `LogLine` are now `Codable` too. Plugins that don't adopt it work as they did, and release builds get stand-ins.

- DD-89: the plugin-authoring guide (Writing Global and Local Plugins, "Intercepting the app's calls") states the contract an interception plugin keeps: install is idempotent, uninstall restores exactly what install changed, the app sees the same results, capture is bounded and the drawer's own activity is left out. The Network, Disk I/O, Location and View Inspector tests check it through a shared test-only target, `DebugDrawerInterceptionContract`. View Inspector's render counts now start with its install rather than at launch, and keep at most 1,000 names, dropping the oldest.
- DD-93: a plugin's model can be read and driven from another process. `DebugDrawerTransport` is one protocol a viewer holds, chosen per connection at run time, that hands out the `DebugDrawerPluginTransport` a plugin's view already draws from: `DebugDrawerInProcessTransport` in the app's own process, `DebugDrawerSocketTransport` over a Unix domain socket while the app runs, and `DebugDrawerAppGroupStoreTransport` from a shared directory, such as an app group's container, that keeps the last snapshots and queues commands while the app is suspended. The app offers its models in a `DebugDrawerModelRegistry`, by plugin ID, and serves it with `DebugDrawerSocketServer` and `DebugDrawerAppGroupStoreServer`; snapshots and commands travel as JSON, framed by length on a stream. Everything builds on every platform core does, and release builds get stand-ins that connect to nothing.
- DD-19: `DebugDrawerRemote`, a new library, serves plugin models to a viewer on another device over the local network, so a phone's Network and Console can be read on a Mac. `DebugDrawerNetworkServer` listens over TCP and advertises `_debugdrawer._tcp` over Bonjour only once the app calls `start()` (`DebugDrawerNetworkServerConfiguration` picks the name and port, or `.loopback` for 127.0.0.1 alone); each viewer that connects is listed in `pairingRequests` with a new six-digit code for the device to show, and pairs only by sending that code back, while a wrong code, a rejection or anything sent before pairing closes it. On the viewer's side `DebugDrawerNetworkBrowser` lists the devices advertising and `DebugDrawerNetworkTransport`, a `DebugDrawerTransport`, pairs with `pair(code:)` and hands out the plugins' transports. The README lists the Info.plist keys it needs (`NSLocalNetworkUsageDescription`, `NSBonjourServices`); release builds get stand-ins that never listen, browse or connect.

### Changed

- DD-264: a toast goes away by itself `DebugDrawer.toastLifetime` (6) seconds after its last post, each post starting the countdown again; it stays while the pointer is over it or VoiceOver's focus is on it, and goes that long after they leave. Its dismiss button's hit area is the toast's top trailing corner, 44 points square on touch screens and 22 on the Mac, with the icon where it was; tvOS keeps the button in the row, reached by focus.
- DD-242: the Network, Console and View Inspector plugins capture into the store of the drawer that installed them last, rather than always into the shared one: installing one on a `DebugDrawer()` sends the app's requests, log lines and render counts to that drawer's plugin, and removing it hands them back to the drawer that installed it before (the shared drawer, in an app). Network's mock rules and conditions follow the same drawer. Each of these plugins, and Accessibility and Tweaks, takes a store or model of its own through an internal initializer, which their tests build over hand-written fakes. `install*()`, `.shared` and what an app that uses only the shared drawer sees are unchanged.
- DD-226: `DebugDrawer` gains `open()` and `close()` (each harmless when repeated; no-ops in release), and setting `isOpen` is deprecated in favor of them and `toggle()`, while reading it and `$isOpen` work as before; `DebugDrawerPlugin` is now isolated to the main actor, so a plugin type is main-actor and one that declares its own computed `id` marks it `nonisolated`.
- DD-223: the xcodebuild recipes (`just test-ios`, and `just spm-test`'s and `just spm`'s visionOS, tvOS, watchOS and Mac Catalyst stages) build with Xcode's compilation caching in one store every checkout shares, `~/Library/Caches/debugdrawer-xcode-cas`, so a new worktree replays what another already compiled instead of building it all again (`scripts/xcode_cache.py`). `just test-ios` still compiles the test targets in each checkout, since its snapshot tests find their references through `#filePath`; SwiftPM's `swift build` has no such cache, so `just spm-test`'s Mac stage compiles everything as before.
- DD-139: App Info is built on the model/view split too: `AppInfoModel` holds the bundle's identifier, version and build with the commit, branch and CI build, the device and operating system, the process (its ID, arguments, start, debugger, memory footprint and uptime), the network's reachability and the provisioning profile and entitlements, read as a `Codable` `AppInfoSnapshot` and changed with `AppInfoCommand` (start and stop refreshing, counted with the drawers that show the plugin; read again now), and the plugin's view draws from it through a `DebugDrawerPluginTransport`, keeping the wording, units, Copy Info and the bug report's `app-info.json`. The Info.plist, `ProcessInfo` and the screen, the kernel's process start and footprint, the signing, the wall clock, the 2 s timer and the network path monitor sit behind services the model takes at init. `AppInfoBuildMetadata` is `Codable`. It still reads only while a drawer shows the plugin or a report is made, and what the drawer shows and does is unchanged.
- DD-138: Energy is built on the model/view split too: `EnergyMonitor`, the store the app already starts and stops, is now its model, read as a `Codable` `EnergySnapshot` (CPU use and its history, the cores it is measured against, the battery and its history, the power source, the thermal state and Low Power Mode, and whether it samples) and changed with `EnergyCommand` (start, stop, and reset, which starts the history over), and the plugin's view draws from it through a `DebugDrawerPluginTransport` and labels and gauges the values itself. The battery, the thermal state, Low Power Mode, the process's CPU, the 1-second timer and the clock sit behind services the monitor takes at init, read only while it samples; battery, thermal and Low Power Mode changes the system announces reach the snapshot as they happen. What the drawer shows and does is unchanged, and `EnergyMonitor`'s existing API stays as it was.
- DD-137: Performance is built on the model/view split too: `PerformanceModel` holds the frame rate, frames dropped, memory footprint and its peak against the device's memory, each second's frame rate and footprint, the threads by CPU and when a memory warning was last posted, read as a `Codable` `PerformanceSnapshot` and changed with `PerformanceCommand` (start and stop sampling, counted with the drawers that show the plugin; drop the history; keep a longer or shorter history; post a memory warning), and the plugin's view and HUD readout draw from it through a `DebugDrawerPluginTransport`, keeping the gauges, sparklines, averages and units. The display link and its timer, Mach's thread list, the kernel's footprint and UIKit's memory warning sit behind services the model takes at init. It still samples only while a drawer shows the plugin, and what the drawer shows and does is unchanged.
- DD-136: Disk I/O is built on the model/view split too: `DiskIOModel` holds the recorded calls and their totals, the filter, whether recording is paused and the volume's size and free space, read as a `Codable` `DiskIOSnapshot` and changed with `DiskIOCommand` (filter, clear, pause or resume, read the volume), and the plugin's view draws from it through a `DebugDrawerPluginTransport`; `IOEvent` (its error as domain, code and description), `IOEvent.Operation` and `DiskIOTotals` are now `Codable`, and `IOEvent` `Equatable`. The recorded calls and reading the volume sit behind services the model takes at init, and a Pause button stops recording until Resume. `installDiskIO()`, `DiskIOStore` and what is recorded work as before.
- DD-135: Keychain is built on the model/view split too: `KeychainModel` holds the app's keychain items (class, service, account, label, access group, dates and every attribute), the filter, the open item, the add or edit form and the last refusal, read as a `Codable` `KeychainSnapshot` and changed with `KeychainCommand` (refresh, filter, open an item to reveal its password, add, edit, delete one, delete the ones shown), and the plugin's view draws from it through a `DebugDrawerPluginTransport`; Copy stays in the view. The snapshot holds item metadata only, saying whether a password was read or refused: passwords stay in the app's process, where the plugin's own view reads them from the model, so no transport can carry one out. The Security framework's `SecItem` calls sit behind a service the model takes at init. What the drawer shows and does is unchanged.
- DD-134: UserDefaults is built on the model/view split too: `UserDefaultsModel` holds the suites offered, the one shown, its keys with their values and domains, and the filters, read as a `Codable` `UserDefaultsSnapshot` (every property-list value kind included) and changed with `UserDefaultsCommand` (pick a suite, filter, show other domains, set, add, remove, reload), and the plugin's view draws from it through a `DebugDrawerPluginTransport`; Copy Value stays in the view. Reading, writing and removing keys in the suites, and the change notification, sit behind a service the model takes at init. `UserDefaultsBrowser.install(suites:)` works as before, and what the drawer shows and does is unchanged.
- DD-132: Screenshot is built on the model/view split too: `ScreenshotModel` holds whether a capture hides the drawer, the last capture (its PNG, size, scale, time and file name) and where it went, read as a `Codable` `ScreenshotSnapshot` and changed with `ScreenshotCommand` (capture, save, copy, clear), and the plugin's view draws from it through a `DebugDrawerPluginTransport`; writing the clipboard and the save panel stay in the view. Drawing the window and writing to the Desktop sit behind services the model takes at init, and a Clear button drops the last capture. What the drawer shows and does is otherwise unchanged.
